Request to production

Eleven steps, and none of them is “hope”.

A request becomes a job with a validated plan and its own worktree. It builds, then faces five gates. Failure sends it to a repair loop with a fixed budget, never an open-ended retry.

Request Plan Five gateslint · tests · code review · security · design Merge Deploy Live

A gate says no, and the job goes back to repair — five rounds, then a person. Nothing reaches Merge that a gate refused.

The control boundary

AI proposes. Code decides.

AI runs three steps — plan, build, repair. It never decides. Every gate verdict, every merge and every deploy is ordinary deterministic code, so no model can approve its own work or reach production on its own.

The boundary is enforced by tool policy and the runner, not by asking a model to behave.

Five gates, fail closed

A change that cannot prove itself does not land.

Lint, tests, code review, security and design each return their own verdict. A tool that fails to run counts as a failure, never as a pass. 2,294 changes were stopped before merge; 395 of those by the security gate.

Recovery, with limits

It repairs itself, and it knows when to stop.

881 shipped changes failed a gate first and repaired themselves with nobody watching. Every retry has a named ceiling, so a struggling job burns a budget instead of a weekend.

When a budget runs out the job stops and hands a person its diagnosis, its diff and every command that ran.

Audit trail

The record is written by the database.

Not by the application. A trigger on thirteen tables records every change, with the acting identity bound per transaction. An application bug or a compromised worker cannot produce an unattributed write.

Segregation of duties

Writing, judging, landing and shipping are four different jobs.

Enforced by per-role tool allow-lists, the runner and the role table — not by prompt wording.

Writes

The coder edits only inside its own worktree. It never commits, merges or deploys.

Judges

Reviewer roles are denied write tools entirely and are snapshot-guarded against tampering.

Lands

The merge step is deterministic code, and re-validates the tree that will actually land.

Ships

A deploy-only worker claims nothing else and refuses to start with an AI credential in scope.

A human sign-off can be inserted at merge or promotion through the role matrix, without changing the pipeline.

The change record

Complete at the moment of deployment.

Nothing has to be reconstructed afterwards. Every job carries a validated plan with stories, target files and acceptance criteria; gate results as structured events with the commands that produced them; a decision record written into the repository at merge; and a register row naming the commit and image digest at deploy.

Supply chain

The reviewed commit and the running container are the same artefact.

Lockfile drift blocks at lint. Dependency audits and secret scanning block at security. Release images are signed and addressed by digest; deploy hosts pull by digest, never by tag, and verify with a public key only. The register says so, and can be checked.

Reviewed commit→Merge re-validates the landed tree→Signed image, addressed by digest→Host pulls and verifies by digest

A repository declares the secrets a release needs; the host checks them locally before cutover, and the values never reach the control plane.

Stated before you find them

Three things this does not do.

A pipeline that reports its own weaknesses is easier to govern than one that reports only wins.

AI gates are probabilistic

A model reviewer can miss a defect. No AI verdict stands alone: deterministic scanners and tests sit beside every AI gate.

The cost meter has gaps

Two internal ledgers disagree by about six percent, and 405 jobs have no usage row. The economics report discloses both.

No automatic rollback

By design. A failed cutover never replaces the running release, so there is nothing to roll back; later faults are fixed forward through the gates.
