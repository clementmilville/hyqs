The audit trigger

The application cannot write an unattributed row, and it cannot forge who it was.

Thirteen tables carry a before-insert-update-delete trigger that stamps the acting identity, records a per-column old-to-new diff, and adds three columns the database observes about the connection itself. A direct SQL edit from outside the application is attributed to the database session user. Heartbeat churn is filtered so the log stays readable.

Exposure

Admin → Access → Audit, gated on the view-audit permission, filterable by table, actor and row, day-grouped, with same-minute bursts collapsed. The API returns the forensic columns; the screen does not yet render them.

Retention

The supervisor prunes audit rows older than 90 days on every scan. That is the in-database default; a bank should stream the table to its SIEM or WORM store, and there is no export endpoint yet, so that feed is a database job today.

Not covered

The usage, stage-event, log, hardware and supervisor ledgers carry no trigger and no created-by column. They are append-only by construction, but a direct database edit to them would leave no trace. Stated here so it is not discovered later.

Identity and roles

Invite-only sign-in, eight roles, twenty-four permissions, editable at runtime.

Google or Apple single sign-on, refused without a pending invitation. API tokens are stored as a hash, scoped to one project, and can never satisfy a platform-wide check. Permissions live in a table, edited from the console, with a locked core so a platform admin can never remove the five that would lock everyone out. Hover a role to read it.

The full eight-by-twenty-six matrix, hover a role to read it: Reference.

Three scopes

Project scope through membership, environment scope through environment members (a client approver can hold one permission for one environment without being a project member), and platform scope for the admin permissions. One check function serves both the console and MCP.

Segregation by construction

Automation clients cannot archive. Promoting to production needs a distinct permission from promoting. Applying an offered release on a client host needs yet another, held by the client. Every promotion row records who requested, who applied, when, and which job executed it.

Every write has a principal

Console users, API tokens, MCP clients, workers, the supervisor and the two system services each stamp their own actor prefix, so the audit log can answer "was this a person or the machine" without a lookup.
