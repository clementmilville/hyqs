Before you begin

Give Hyqs a machine it is allowed to use.

Hyqs clones repositories, runs generated commands and test suites, builds containers, and can deploy applications. Install it as an unprivileged user on a dedicated host, for a closed set of people and repositories you trust.

The host

  • Fresh Debian or Ubuntu VPS with sudo and a working systemd --user session.
  • At least 4 GB RAM for one worker, swap configured, and 20 GB free disk.
  • SSH access as the normal user that will own and run Hyqs. Do not install as root.

The accounts

  • A Claude subscription or Anthropic API key for agent work.
  • A GitHub account only if Hyqs should create repositories or push merged changes.
  • Optional domain and email address if the console will be public behind nginx and Let's Encrypt.

Trust boundary. Anyone who can create a project or queue work can cause repository code to run on this host. Hyqs is not hardened for untrusted multi-tenancy; do not colocate it with data or services you would not give the operator account permission to reach.

Step 1 · install

Clone once. Run one idempotent installer.

The installer adds system packages, uv, the Claude CLI, Python and frontend dependencies, Postgres, generated credentials, user services, and optionally nginx with TLS. If a step fails, fix the cause and run the same command again.

  1. Log in as the unprivileged service user.

    Use a real SSH login rather than su, so the user-level systemd session is available.

  2. Clone to the canonical checkout path.
    git clone https://github.com/clementmilville/hyqs.git ~/hyqs-ai
cd ~/hyqs-ai

    The current service units and self-release script intentionally require ~/hyqs-ai.

  3. Choose where provisioned repositories will live.

    Add --github-org acme-inc to the first install command to use an organization. Omit it to use the authenticated GitHub user's personal namespace. The choice is written only on the first install because reruns never overwrite .env.

  4. Choose how the console is reached, then run the installer once.
    # Recommended first install: loopback only
bash deploy/install.sh --github-org acme-inc

# Public console: point DNS here before running
bash deploy/install.sh --domain hyqs.example.com \
  --email you@example.com --github-org acme-inc

    Remove --github-org acme-inc from either example if provisioned repositories should use your personal namespace.

Done means: the installer prints the console address, first-admin credentials, MCP endpoint, and the remaining authentication steps. Keep that final output open for the next steps.

Step 2 · sign in

Open the console without opening the host.

Without a domain, Hyqs listens only on 127.0.0.1:8787. That is deliberate: the console reaches an agent capable of shell and file operations.

Loopback install

From your own computer, keep this tunnel running:

ssh -L 8787:127.0.0.1:8787 \
  hyqs@your-server

Then open http://127.0.0.1:8787.

Domain install

Open the HTTPS address supplied through --domain. The installer verifies DNS before requesting the certificate and keeps the application port bound to loopback behind nginx.

  1. Sign in with the generated admin email and password printed by the installer and saved in .install-credentials.
  2. After the first account exists, remove the bootstrap-only HYQS_ADMIN_EMAIL and HYQS_ADMIN_PASSWORD values from .env, then delete .install-credentials.
  3. Keep account creation invite-only. OAuth matches an existing user or invitation; it never creates an account by itself.
Step 3 · authenticate the agent

Give the worker a model it can call.

A healthy console does not mean the pipeline can build. Agent authentication is deliberately left to the operator and never manufactured by the installer.

Claude subscription

On the host, run the CLI once and complete its sign-in:

claude

The pipeline can then use the logged-in CLI session.

Anthropic API key

Add the key to the installation's private environment file:

ANTHROPIC_API_KEY=...

Restart the services after changing .env.

Back up one value now: HYQS_CREDENTIAL_ENCRYPTION_KEY encrypts stored third-party credentials. If it is lost, those credentials cannot be recovered.

Step 4 · create your first project

No project, no job queue.

Every job belongs to a project and its repository. From the console, choose New Project, then take one of two paths. Both provision a private GitHub repository and open its project workspace.

Before the console
Authenticate GitHub on the host
gh auth login
gh auth status

The account needs permission to create repositories in the personal namespace or organization selected during installation.

Guided

Describe the product

Let the intake interview build the project specification with you.

  1. Open New Project and answer the interview.
  2. Review the live specification: name, problem, users, authentication, features, data model, and stack.
  3. Select Create project when every required field is complete.
ResultRepository + project + epics + an initial wave of jobs. Those jobs are filed automatically from the features you approved.
or
Direct

Start with a blank project

Use this path when you want to file and observe one small first job yourself.

  1. Open New Project.
  2. Select Skip interview — blank project.
  3. Enter the project name and optional description, then select Create blank project.
ResultRepository + empty project workspace. Continue to Step 5 to file the first job manually.

Ready for work: when the project workspace opens, confirm its name and repository, then leave deployment disabled for the first trial. The default agent roster and limits are enough to begin.

Step 5 · first job

Ask for one change whose success is obvious.

If you created a blank project in Step 4, file one small request from its Work page. If you used the guided interview, the approved features have already become jobs; choose the smallest queued one and follow it instead.

A useful first request

Add a health endpoint that returns the application version. Cover it with a regression test, document the endpoint, and do not change deployment configuration.

  1. File the job from the project's Work page and read the resolved title, scope, and epic before it starts.
  2. Watch PLAN turn the request into bounded stories, target files, acceptance criteria, and activation instructions.
  3. Watch BUILD work in an isolated git worktree. The agent edits; the deterministic runner owns commits and pull requests.
  4. Read every gate: lint, tests, review, security, and design review when the UI changes. A failure should enter FIX and repeat the gates, not skip them.
  5. Inspect the result before enabling automatic pushes or deployments for later work: diff, test evidence, findings, usage, cost, and the final commit.

Keep it running

Inspect, update, and recover with the shipped controls.

Hyqs runs as user services with lingering enabled, so it survives logout and reboot. Releases overlap old and new generations and only retire the old one after the replacement proves healthy.

Console logs

journalctl --user -u 'hyqs-web@*' -f

Pipeline logs

journalctl --user -u 'hyqs-pipeline@*' -f

Release an update

cd ~/hyqs-ai
git pull --ff-only
bash deploy/release.sh

Re-run setup

bash deploy/install.sh

The installer is idempotent and never overwrites an existing .env.
