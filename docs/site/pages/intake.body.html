Five doors

Every job records which door it came through and who opened it.

A job carries its source, the acting user and a metadata blob from the moment it is filed. The console, the command line, an MCP client such as Claude.ai or Claude Code, the structured intake interview, and the supervisor itself are the five sources. Nothing enters unattributed.

The intake interview

AI converses. Deterministic code decides when a project is ready.

A new project starts as a structured conversation with an interviewer that has no repository and cannot write code. It fills a specification through six phases. Whether the specification is complete is decided by code that checks nine fields, not by the model saying it is done.

How the model talks to the code

The interviewer emits machine-readable blocks the user never sees: specification updates as JSON patches deep-merged into the draft, a phase marker, and a completion marker. The completion marker is necessary but never sufficient; the nine-field check has the last word.

What confirming does

Pure deterministic seeding, no model call: provision the repository from the chosen blueprint, create a private GitHub repository, then one epic per theme and one job per feature. Foundation themes get priority 20 and no dependencies; every other job depends on all of them and gets priority 10 if the user asked for it, 5 if it was a suggestion.

Resumable by design

Sessions persist with their draft, messages and status, so an interview can be paused for a week. The screen offers resume or start fresh, shows per-session progress, and has an escape hatch: skip the interview and create a blank project.

From idea to a chained wave

The AI proposes. A human clicks to file. The queue never takes orchestration advice.

Three surfaces turn intent into jobs, and all three share one rule: the model cannot file anything. It proposes a list, the person reviews and creates it, and from then on the deterministic queue, dependency gate and collision serialisation own the order.

Job chat

Two modes. Diagnose: root-cause with at least one file and line citation before proposing. Feature: state the trade-offs first. Every proposed job must carry two meaningfully different alternatives, an epic, and its dependencies. The model is told bluntly it cannot file and must never say "I've filed those".

Backlog refine

Anyone with the propose permission can add backlog items and vote; changing their status needs the triage permission. Refining selected items runs the same contract, at most eight jobs, deduplicating overlapping asks. Filing the wave marks the source items converted and links them, so any job can name the backlog items behind it.

Architect

One epic plus a goal in, a job graph out: at most ten jobs, each self-contained with a "done when" clause, narrow allowed paths, a rationale for the shape of the graph. It is grounded in the project's symbol index and the last fifteen decision records. Its own words: "You only draw the map."

MCP

Thirty-eight tools, the same permission checks as the console.

The Model Context Protocol endpoint lets Claude.ai, Claude Code or any automation client drive the pipeline. Interactive users sign in with Google through OAuth 2.1; automation presents a project-scoped API token. Every tool resolves the caller and applies the same membership and permission rules as the console, returning a forbidden error rather than raising.

The full catalogue of 38 tools with their permissions is in the Reference.

Connecting an organisation

  • People: add the endpoint as a remote MCP server in Claude.ai or Claude Code. An OAuth proxy terminates Google sign-in and adds the dynamic registration and resource metadata that Google lacks. Unknown or inactive users get nothing; there is no auto-provisioning.
  • Automation: a project API token, stored as a hash, valid for exactly one project and role.
  • Command line: hyqs-jobs wraps the same tools with exit codes for ok, tool error, transport, forbidden and not found, and either a token or a cached browser sign-in.

Asking questions about a job

The console's job chat runs an explorer agent bound to one project through closures: the project never appears in any tool input, so the model has no parameter with which to name another. Nine read-only tools, a sandbox with no network, a path guard that denies by default, and for the platform's own repository a throwaway worktree rather than the live checkout.

Notifications

One Slack thread per job. The channel shows one line per change.

The first message a job emits becomes the root of a thread with a deep link back to the console; every later message replies in that thread. A generic webhook receives a structured payload instead. Egress is hardened against server-side request forgery: addresses are resolved, pinned, and must be globally routable, with the IPv6 embeddings that fool naive checks unwrapped.

The happy path, in order

  1. 🧭 planning…
  2. 📋 planned 2 stories. Building…
  3. 🔨 built and pushed. Linting… with the pull request link
  4. 🧹 lint passed. Testing…
  5. ✅ tests passed. Reviewing…
  6. 🔎 review passed. Running security check…
  7. 🔒 security passed. Merging… (🎨 design review when the diff touches the UI)
  8. 🔀 squash-merged. Deploying…
  9. 🚀 deployed. Done. Dependents unblocked

The detours, each with its own message

  • 🛠️ failure detected, self-healing, attempt n of 5
  • 🔁 fix applied, re-linting
  • 🔀 merge conflict, resolving, rebase n of 5
  • 🔄 base advanced, re-verifying before merge
  • ⏱️ stage timed out, retrying, n of 2
  • ⏸️ provider hit its limit, pausing until a time, or resuming on the other provider
  • ✂️ plan too large, split into n jobs
  • ♻️ restarting to apply a pipeline update
  • ❌ failed, with stage, attempts and reason
  • ⚠️ supervisor escalations carry an explicit needs-attention type and a reason; ℹ️ and 🩺 lines record automatic requeues and diagnoses

Bot tokens are stored encrypted with a key that must be provisioned; without it, no plaintext is ever written.
