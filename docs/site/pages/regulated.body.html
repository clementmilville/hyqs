What we would tell your auditor first

The limits, stated before you find them.

A pipeline that reports its own weaknesses is easier to govern than one that reports only wins. These are the four we lead with.

AI gates are probabilistic

A model reviewer can miss a defect. That is why no AI verdict stands alone: deterministic scanners and tests sit beside every AI gate, the merged tree is re-validated, and any oscillation escalates to a person. Treat the AI reviewers as a strong additional lens, and keep your human approval where your policy requires it, at merge or at promotion.

The cost meter has known gaps

The economics report discloses that two internal ledgers disagree by about six percent, that 405 ordinary jobs have no usage row, and that most historical rows lack model metadata. Its recommendation, a per-stage-attempt ledger finalised on every exit path and reconciled against provider logs, is on the roadmap. Quote the headline with the audit beside it.

No automatic rollback, by design

A failed cutover never replaces the running release, so there is nothing to roll back. A deploy that passed its probe but misbehaves later is fixed forward by a filed job that goes through every gate, capped at three per project and escalated to a person if the fix itself fails. If your policy requires a one-click revert to the previous digest, that is a promotion of the prior release, and it uses the same ledger.

Model traffic leaves your perimeter

Source context is sent to the model provider during plan, build, fix and review. Everything else is self-hosted. Placing that one flow under an enterprise agreement with the retention terms your policy requires is the first onboarding task, and the audit log lets you prove which repositories and stages generated it.

The control map

Mapped to the controls your second line already asks for.

The questions are the ones a change advisory board, an ICT risk function under DORA, or an ISO 27001 auditor actually asks. The answers are mechanisms, with the guarantee each one provides and the place it lives.

Segregation of duties

Can the author approve or ship their own change?
Mechanism
  • The coder role can edit only inside its worktree; it never commits, merges or deploys.
  • Reviewer roles are denied write tools and snapshot-guarded.
  • A deploy-only worker claims nothing but the deploy step and refuses to start with an AI credential in scope.
  • Promoting to a production environment requires the distinct prod promoter permission; applying an offered release on a client host requires client approver. Every promotion row records who requested it, who applied it, when, and which deploy job executed it.
Guarantee

Writing, judging, landing and shipping are four different principals with four different tool sets, enforced by the SDK, the runner and the role table, not by prompt wording.

Independent review

Is there a real second pair of eyes?
Mechanism
  • Three independent lenses on every diff: code review, security review, and five deterministic scanners, each with its own verdict.
  • Reviewers see the prior attempt's verdict so re-reviews converge on the same issues rather than inventing new ones.
  • When review and security demand mutually exclusive changes, the alternation is detected and the job is escalated to a human ruling.
Guarantee

No single model call can pass a change. A human sign-off step can be inserted at merge or promotion through the role matrix without changing the pipeline.

Change management

Can you show me the plan, the test evidence and the approval for change X?
Mechanism
  • Every change is a job with a validated plan (stories, target files, acceptance criteria, UI impact, activation instructions).
  • Test, lint and gate results are events with structured detail and the commands that produced them.
  • The merge writes an ADR into the repository; the deploy writes a register row with the commit and image digest.
Guarantee

The change record is complete at the moment of deployment, linkable from the PR, the console and the Slack thread that tracked the job.

Audit trail and non-repudiation

Who changed what, when, from where, and can the application lie about it?
Mechanism
  • Audit rows are written by a database trigger, not by application code, with connection-level forensics.
  • The acting identity is bound per transaction: user, API token, MCP client, worker, supervisor, or database session user as the fallback.
  • Jobs are soft-archived, never deleted.
Guarantee

An application bug or a compromised worker cannot produce an unattributed write. Export the table to your SIEM or WORM store for retention beyond the 90-day in-database default.

Least privilege

What can an agent, a token or a client actually reach?
Mechanism
  • Per-role tool allow-lists at the SDK level; the question-answering explorer runs sandboxed with no network and a deny-by-default path guard, including an explicit deny on reading .env.
  • Project API tokens are hard-scoped to one project. Environment members can hold one permission for one environment without project membership.
  • Webhook egress is SSRF-hardened: addresses are resolved and pinned, redirects refused, NAT64 and 6to4 embeddings unwrapped.
Guarantee

Blast radius of any single principal is one project, one role's tools, and for gates, zero writes.

Secure software supply chain

How do you know what is running is what was reviewed?
Mechanism
  • Lockfile drift blocks at lint; pip-audit and a baseline-aware npm audit block at security; secrets scanning on every changed file.
  • Release images are pushed to a private registry, signed with cosign, and addressed by digest. Deploy hosts pull by digest, never by tag, and verify with a public key only; verification fails closed if the key is absent, and push credentials never exist on a deploy host.
  • A repository declares the secrets a release needs; the deploy host checks presence and format locally before cutover and the values never reach the control plane.
  • Merge validation re-tests the tree that will actually land, not just the branch tip.
Guarantee

The reviewed commit, the signed digest and the deployed digest are the same artefact, and the register says so.

Operational resilience

What happens when a host dies, a provider throttles, or a deploy goes wrong?
Mechanism
  • Workers hold 90-second leases renewed every 30 seconds; a dead host's job is reclaimed by the next claim on any host. Coordination is a plain relational database, no broker to operate.
  • Provider limits pause only that provider; jobs routed elsewhere and all deterministic steps keep flowing.
  • Deploys start a probe container first, with all capabilities dropped, no port binding and a throwaway copy of the data directory; the last-good container keeps serving until the probe passes. The pipeline releases itself blue-green with a 40-minute drain. Bad deploys are fixed forward by a filed job under a loop guard, never rolled back silently.
Guarantee

Loss of a worker, a provider, or a deploy attempt is a recoverable state with a named remediation, not an incident to be reconstructed.

Data residency

Where does our source code go?
Mechanism
  • Hyqs is self-hosted: the database, workers, registry and console run on your hosts. Client and production deploy hosts run a constrained deployer that pulls signed images by digest; a fully air-gapped bundle install is designed but not yet built.
  • The single external dependency is the model provider. The Claude backend uses the Claude Agent SDK, which can be pointed at Anthropic directly or at a cloud-hosted enterprise endpoint; the Codex backend is a second, independent provider.
Guarantee

Code and evidence stay in your perimeter. Model traffic is the one flow to place under your enterprise agreement, and it is the only one.
