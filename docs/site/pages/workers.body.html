Topology

Symmetric workers, one database, no broker.

A worker is a plain process that claims jobs from a shared database under one advisory lock. There is no scheduler service, no message queue and no agent daemon. Run one process on a laptop or thirty across ten hosts; the claim is the same. Only one thing is elected, the supervisor, and only one thing is pinned, the deployer.

Executor

An async slot inside a hyqs-pipeline process. Claims any stage for any project it has capacity for, holds a 90-second lease renewed every 30 seconds, and runs one stage at a time. Dies, and its job is reclaimed by the next claim on any host.

Supervisor

Runs inside every pipeline process but is a singleton fleet-wide: a database session-level advisory lock elects one leader, standbys retry every 30 seconds. Every 120 seconds it reclaims orphaned slots, classifies failed jobs and applies bounded remediations. It never calls a model to decide anything.

Deployer

hyqs-pipeline --deployer: a constrained worker that claims only the deploy step, only for environments pinned to its enrolled host, and refuses to start without a host name. It never constructs an AI backend and carries no model credential.

Sizing

Three scaling axes that compose. One roster that caps them.

Slots per process, processes per host, hosts per fleet. Every combination shares the same database and the same claim. What actually runs in parallel for a project is then capped by its agent roster, so capacity is a policy you edit in the console, not a deployment you redo.

The agent roster

An agent is a row: provider, model, the tasks it may take, and how many at once.

Each project keeps its own roster. At claim time the runner picks the lowest-id enabled agent that lists the needed task, whose provider is not paused, and that still has concurrency left. Pinning a stronger model to review and a cheaper one to build is two rows, not a code change. Running Claude and Codex side by side is two rows with different providers.

Deterministic steps (lint, test, merge, deploy) need no agent. The design-review and merge-verify gates draw on the review task. A provider hitting its limit pauses only that provider's rows; the others keep claiming.

How a claim is decided, in order

  1. Reclaim the dead. Any running job whose lease expired goes back to pending, owner cleared.
  2. Select candidates. Pending jobs whose dependencies are done or resolved and whose rebase backoff has elapsed, ordered by effective priority then id. At most 50 are considered.
  3. Skip collisions. A job whose declared file scope overlaps a running job's scope waits.
  4. Apply worker limits. A deploy-only worker takes deploy steps only; a pinned environment's deploy step goes only to its host.
  5. Pick an agent. Lowest-id enabled agent with the task, provider not paused, running below its cap. Deterministic steps skip this.
  6. Write the lease. Status running, owner, lease, agent and provider stamped in one transaction under the claim lock.

What a job knows about its executor

Every event a job records carries the agent id that ran it, so the timeline shows Coder (Sonnet 5) · claude · claude-sonnet-5 per stage and the cost tab breaks spend down by stage, model and provider. When a job is requeued to another provider after a pause, the failover event names both.

  • Effective priority = base + remediation boost 20 + critical-path boost up to 30 + aging up to 15.
  • A fast path keeps a job on the same worker across consecutive deterministic steps, skipping the requeue round trip.
  • Rate limits are translated by each backend into one typed signal; auth and billing errors are not, so a bad key fails loudly instead of pausing.
Tool policies by role

What an agent can touch is decided by the SDK, not by the prompt.

Four roles, four tool sets. The coder writes only inside its worktree. Planners and reviewers have their write tools removed at the SDK level, and every gate runs under a snapshot-and-restore guard on top. The explorer that answers questions about a job is sandboxed with no network at all. The exact tool list per role is in the Reference.

The supervisor

One elected process. A fixed scan. Every action capped and recorded.

The supervisor is the control plane's only loop, and it is deliberately AI-free: classification, routing, election and caps are Python and SQL. A model is consulted only where a rule explicitly hands it a closed menu, and its answer is validated by a whitelist before anything runs.

One scan, every 120 seconds, in this order

  1. Reclaim orphaned slots whose job is no longer running or deploying, keyed on job status, never on heartbeat age.
  2. Check fleet liveness. Every slot busy and no job advanced in 5 minutes means a wedge; alert once per episode.
  3. Repoint split orphans and minimise automatic dependency edges per project.
  4. Alert on stale jobs older than 24 hours.
  5. Repair dependency cycles, but only by cutting one edge from two provable classes; otherwise alert.
  6. Classify every failed job into one of 17 classes, typed codes first, and apply the matching remediation: requeue, reconcile, file a fix job, or hand to a person.
  7. Reconcile blocked dependents, sweep stranded deploying jobs, collect orphaned worktrees and branches.
  8. Housekeeping: prune the audit log at 90 days, remove dead job containers, prune the build cache every 6 hours, remove images of inactive jobs.

Liveness, drain, release

A worker proves it is alive by writing a heartbeat, not by existing.

Systemd reporting "active" is not proof: a crash-looping unit is active. The health check and the release script both require a fresh heartbeat row from a process in the new unit's own cgroup before the old fleet is asked to stop.

Heartbeat and reclaim

Slots heartbeat on claim, on every fast-path hop, and every 30 seconds while a stage runs; their rows drive the fleet view. Two independent recovery layers exist because a hung SDK teardown once kept renewing "busy" for eight hours: orphaned-slot reclaim keyed on job status, and the wedge detector.

Signals and drain

The first SIGTERM starts a graceful drain with a 40-minute ceiling so a mid-flight build survives a release; a second SIGTERM stops immediately. SIGUSR1 is the shorter operator drain at 5 minutes. Draining slots stop claiming, finish their stage, and mark themselves draining in the fleet view.

Blue-green self-release

The pipeline deploys itself by starting a new generation unit beside the old, waiting for that unit's heartbeat, and only then stopping the old. The web console does the same with port reuse, gated on the health endpoint returning a PID from the new unit. If the new generation never proves itself, it is stopped and the old fleet keeps serving.

Hardware accounting per stage

Every deterministic subprocess (lint, tests, deploy, git) runs in a transient systemd scope so the runner can read the cgroup's CPU seconds, peak memory and I/O when it finishes, plus a coarse network delta. AI stages record their wall time. The figures land per job, stage and attempt and show on the job's Hardware tab. Missing cgroup support degrades to nulls, never to a failed job.
