A project's first minute

Register a repository, or let the interview provision one that already deploys.

Three doors: register an existing repository, provision a new one from a blueprint, or confirm an intake interview that does the provisioning for you. A provisioned project gets a private GitHub repository, an initial commit, a deterministic port, an nginx virtual host, and a compose file that already respects the shared-host contract.

A provisioned project deploys on its first day, with loopback ports and dropped capabilities from the first commit.

What a blueprint scaffolds

README, a conventions file, a gitignore that blocks every env file, a Dockerfile, an env example, and a compose file that binds the web port to loopback only, drops all capabilities, forbids privilege escalation, runs as an unprivileged user and caps memory and CPU. The fastapi blueprint adds a health endpoint and a real test.

Port and vhost

The port is 8100 plus the project id, so it never collides and needs no registry. The vhost is rendered per domain, validated with an nginx test before it is committed, removed again if validation fails, and only then reloaded, under a sudo rule narrowed to exactly those two commands.

Rollback on failure

Any failure in scaffolding, the initial commit or GitHub creation deletes the half-made repository so nothing survives in an undefined state.

Deploy modes

Five ways to ship. Pick one to see its gates, in order.

The deploy stage first syncs the checkout fast-forward only, refusing if it is dirty, then dispatches on what the project is: the platform itself, a command, a single container, a compose stack, or a signed release pulled by digest. Every mode ends with the same question, did the service come live, and a no is a failed job, never a rollback.

Five modes, one question: did it come live. A no is a failed job, never a rollback.

Probe-first cutover

The last-good container keeps serving until the new one has proved itself three times.

A single-container deploy never replaces what is running until a throwaway probe of the new image has started, answered its health URL and exposed every declared environment variable. The probe has no port, no restart policy, all capabilities dropped, and a disposable copy of the data directory so a migration cannot touch live data.

The last-good container keeps serving until the new one proves itself three times.

Environments and promotions

Build once, promote by digest. Push to your environments, offer to a client's.

Every project has an implicit production environment on auto-deploy, which is why a single-environment project behaves as before. Add environments and a release becomes a signed image addressed by digest that is promoted, not rebuilt. A promotion is a ledger row with a validated state machine; click a state to see what may follow it.

Build once, promote by digest. Push to your environments, offer to a client's.

Promote

Our-side push. Supersedes prior promotions on the target, creates the row as dispatched, and enqueues a deploy-only job carrying environment, release and promotion ids. Promoting the release that is already current is a no-op. Production targets require the separate promote-to-production permission.

Offer

Client-initiated apply. Creates the row as available and enqueues nothing. On the client's host, hyqs-pipeline apply finds the offer for its enrolled environments, pulls by digest, verifies the signature, checks the declared secrets exist locally, and runs the same probe-first cutover. The client can decline with a recorded reason. Secret values never leave the client host.

The ledger row

Project, release, target environment, kind, state, who requested and when, who applied and when, and the deploy job that executed it. Not built yet: a console screen for environments and promotions; today this surface is the CLI and MCP.

Supply chain and secrets

The reviewed commit, the signed digest and the deployed digest are the same artefact.

A private OCI registry with two accounts, one that can push and one that can only read. Images are signed on the build host and verified on the deploy host with a public key that fails closed when absent. Secrets are declared in the repository and checked for presence on the host, never read into the control plane.

The reviewed commit, the signed digest and the deployed digest are the same artefact.

Registry and signing

Zot, bound to loopback behind nginx, chosen for native referrers so signatures live beside images. Push credentials and the signing key exist only on the build host; pull credentials and the public key only on deploy hosts. A five-step smoke check proves the two accounts are scoped correctly, ending with a pull by digest that must match the push.

Secrets contract

A repository declares the secrets a release needs with owner, required flag and a format regex. Before a pulled release is cut over, the host checks each name resolves and matches its format from a local env file. Values are never returned, logged or persisted. A required-env manifest additionally checks the running container's environment, catching a variable set on the host but never mapped into a service.

Leak prevention

Compose deploys pass an allow-listed environment only, so the pipeline's own database password or model keys can never reach a project container through variable substitution. The installer for a client host creates the secrets directory with owner-only permissions and never sets a value itself.

Running it

Deployed is not the same as serving. The runtime screen tells the difference.

Three independent signals are combined for every application: container state from Docker, a single public health probe, and a three-way port comparison between configuration, the container's published port and the nginx vhost. The last one catches the dead-port misroute where the container is alive but traffic goes elsewhere, and prints the fix command.

Deployed and serving are two different signals, and the runtime screen shows both.

Controls

  • Deploy now and restart file a deploy-only job through the same health-gated path; a restart is never a raw destroy-and-recreate.
  • Stop requires the queue permission, an explicit confirmation, and is logged with project, actor and mode.
  • Start reuses the same secrets link and environment allow-list as deploy so nothing drifts.
  • Logs per compose service, validated against the service list, tail capped at 500.
  • Resync vhost re-applies the virtual host idempotently, via MCP.

Housekeeping the supervisor does

  • Finalises deploying jobs whose fleet restarted, by ancestry of the deployed commit rather than equality, so a later merge does not strand them.
  • Removes containers of inactive jobs and dead probe containers; leaves a live probe alone.
  • Prunes the build cache every six hours with a 72-hour grace, after the cache once reached 133 GB.
  • Removes images of inactive jobs, never base images.
  • Alerts when an application has trailed the main branch for six hours, at most once per twelve.

Designed, not built. Air-gapped installation and per-host pull credentials are marked as future work; today's tier is connected hosts. Environments and promotions have no console screen. Runtime lifecycle actions are logged, not written to the audit table. Host key rotation has no path yet. These are stated on the regulated-industries page as well.
